# Engineering Guide

Operational standards for working in this repo. Read before changing code.

## Commands

Toolchain: Flutter 3.47 (bundles Dart), pinned in `mise.toml`. Run `mise install` once. Copy `env.example.json` to `env.json` before `mise run dev`.

| Command | Scope |
|---|---|
| `mise run install` | Resolve deps from `pubspec.yaml` / `pubspec.lock`. Usually implicit: `flutter run`/`test`/`analyze` resolve deps themselves. (`flutter pub get`) |
| `mise run codegen` | Generate `*.g.dart` / `*.freezed.dart`. Runs automatically before `analyze` and `test`. (`dart run build_runner build`) |
| `mise run codegen:watch` | Regenerate on save while developing. (`dart run build_runner watch`) |
| `mise run dev` | Run on a device/emulator/browser with hot reload, env from `env.json`. (`flutter run --dart-define-from-file=env.json`) |
| `mise run format` | Format all Dart files in place. (`dart format .`) |
| `mise run format:check` | Fail if any file needs formatting. (`dart format --output=none --set-exit-if-changed .`) |
| `mise run analyze` | Static types + lints from `analysis_options.yaml`. This is the type checker; there is no separate typecheck. (`flutter analyze`) |
| `mise run test` | Unit + widget tests under `test/`. Does not run `integration_test/`. (`flutter test`) |
| `mise run test:integration` | Device flows under `integration_test/`. Needs a connected device or emulator (`flutter devices`). (`flutter test integration_test`) |
| `mise run build:android` | Release app bundle to `build/app/outputs/`. (`flutter build appbundle --dart-define-from-file=env.json`) |
| `mise run build:ios` | Release ipa to `build/ios/ipa/`. macOS + Xcode only. (`flutter build ipa --dart-define-from-file=env.json`) |
| `mise run build:web` | Release web bundle to `build/web/`. (`flutter build web --dart-define-from-file=env.json`) |
| `mise run check` | format:check + analyze + test. |

State command scope exactly. Do not say "all tests pass" unless the command you ran covers every suite - `mise run test` skips `integration_test/`; check `mise.toml` and `pubspec.yaml` first.

## Dart

Recommended `analysis_options.yaml`:

```yaml
include: package:flutter_lints/flutter.yaml
analyzer:
  language:
    strict-casts: true
    strict-inference: true
    strict-raw-types: true
  exclude:
    - "**/*.g.dart"
    - "**/*.freezed.dart"
linter:
  rules:
    - prefer_const_constructors
    - prefer_final_locals
    - always_declare_return_types
    - avoid_dynamic_calls
```

- Sound null safety. No `dynamic` except at JSON/platform-channel boundaries; isolate and comment. No `!` without a guarding comment.
- Prefer `final` locals and fields. Mutable state belongs in notifiers, not in widgets or top-level variables.
- Model closed state sets as `sealed` classes and handle them with exhaustive `switch` expressions.
- Parse unknown JSON at the data-layer boundary into freezed models, then trust the typed value internally.

## Flutter Patterns

- Widgets small and single-purpose: `StatelessWidget` or `ConsumerWidget` by default.
- `const` constructors wherever possible so the framework can skip rebuilds.
- Extract a widget class instead of a helper method that returns a widget.
- Async surfaces render loading / data / error explicitly via `AsyncValue.when`. Render useful empty/error states - do not silently swallow failures.
- Theme via `ThemeData` + `ColorScheme.fromSeed` in `lib/core/theme.dart`. No hardcoded colors in widgets; read `Theme.of(context)`.
- Navigation only through `go_router` (`context.go` / `context.push`). Routes are defined in `lib/core/router.dart`.

## State Management

Riverpod with codegen (`riverpod_generator`).

- `@riverpod` functions for derived or async reads.
- `@riverpod class X extends _$X` notifiers for mutable state.
- Widgets `ref.watch` in `build`, `ref.read` in callbacks.
- Repositories are exposed as providers so tests can override them.
- No global singletons. No `setState` for anything shared beyond one widget.
- Forms own their own local state (`TextEditingController` / `Form` + validators).

## Code Generation

- Deps: `build_runner` (dev), `freezed` (dev) + `freezed_annotation`, `json_serializable` (dev) + `json_annotation`, `riverpod_generator` (dev) + `riverpod_annotation`.
- Every annotated file declares its parts: `part 'x.g.dart';` and/or `part 'x.freezed.dart';`.
- Generated files are gitignored (`*.g.dart`, `*.freezed.dart`) and regenerated by `mise run codegen` (automatically before `analyze` and `test`). Use `mise run codegen:watch` while developing.
- Do not hand-edit generated files. Change the source and regenerate.

## Testing

- `flutter test` for unit + widget tests. Widget tests use `testWidgets` and `WidgetTester.pumpWidget`, wrapped in `ProviderScope(overrides: [...])`.
- Override providers with fakes. Mock repositories with `mocktail`; never mock HTTP at widget level.
- Provider unit tests use `ProviderContainer.test()` (or `ProviderContainer` + `addTearDown(container.dispose)`).
- Device flows live in `integration_test/` and run via `mise run test:integration`.
- Golden tests are optional. If used, update with `flutter test --update-goldens` and review the image diffs.
- Run `mise run check` before claiming a change is ready.

## Boundaries

- Features never import another feature's `data/`. Cross-feature shared code lives in `lib/core/`.
- Repositories in `data/` own HTTP (TODO: pick `dio` or `http`) and return domain models.
- `presentation/` depends on providers, never on repositories directly.

## Devcontainer

The devcontainer covers analyze, test, web, and Android builds only. iOS builds and the iOS simulator need macOS + Xcode on the host. To preview the web build inside the container, run `flutter run -d web-server --web-port 8080` (port 8080 is forwarded).

## Search Scope

When grepping, finding, or reading within the repo, exclude dependency, cache, generated, and build output. They pollute results, slow `find`, and hold no source-of-truth content.

- `.dart_tool/`
- `build/`
- `ios/Pods/`, `ios/.symlinks/`
- `android/.gradle/`
- `.flutter-plugins*`
- `coverage/`
- `*.g.dart`, `*.freezed.dart`

Examples (the `rg -g` globs are only needed when running outside the repo's `.gitignore` scope, e.g. with `--no-ignore`):

```bash
rg --hidden -g '!{.dart_tool,build,ios/Pods,ios/.symlinks,android/.gradle,coverage}/**' -g '!*.{g,freezed}.dart' -g '!.flutter-plugins*' '<pattern>'
find . -type d \( -name .dart_tool -o -name build -o -name Pods -o -name .symlinks -o -name .gradle -o -name coverage \) -prune -o -type f ! -name '*.g.dart' ! -name '*.freezed.dart' -print
```

Metadata reads are fine when the file itself is the source of truth: `pubspec.yaml`, `pubspec.lock`, `analysis_options.yaml`.

## Settings

`lib/core/env.dart` is the only file that calls `String.fromEnvironment`. Everything else imports `Env`.

```dart
abstract final class Env {
  static const apiBaseUrl = String.fromEnvironment('API_BASE_URL');
  static const flavor = String.fromEnvironment('FLAVOR', defaultValue: 'dev');
}
```

Rules:

- Declarations must be `const`. Non-const `String.fromEnvironment` calls return the default at runtime.
- Values come from `env.json` via `--dart-define-from-file=env.json`. `env.json` is gitignored; `env.example.json` is committed with names and dummy values.
- Values are compiled into the app binary and can be extracted. Never put secrets there; secrets stay server-side.
- New var: extend `Env` and add it to `env.example.json`.
- Tests read `Env` defaults or override the providers that consume it.

## Safety: Do Not Read

- `.env`, `.env.*` (except `.env.example`)
- `env.json` (use `env.example.json`)
- `.secrets/`, `secrets.toml`, `.envrc`
- `*.pem`, `*.key`, `*.p8`, `*.p12`, `*.pfx`
- Signing material: `android/key.properties`, `*.jks`, `*.keystore`, `*.mobileprovision`
- Firebase config: `google-services.json`, `GoogleService-Info.plist`
- Cloud credential files (`~/.aws/credentials`, service account JSON)
- Local DSNs, connection strings, bearer headers checked in by accident
- Tokens, API keys, session cookies pasted into commits
- Provider response payloads that contain user data

Metadata reads are fine: `pubspec.yaml`, `pubspec.lock`, `analysis_options.yaml`, `env.example.json`.

Use `env.example.json` only for variable names. Preserve unrelated dirty work - never revert files you did not intentionally change.

## Commits

- **One concern per commit.** Do not bundle a refactor with a feature with a dep bump.
- **Subject <= 72 chars, imperative mood.** Conventional prefix when useful (`feat:`, `fix:`, `chore:`, `refactor:`, `docs:`).
- **Body explains *why*, not *what*.** The diff shows what.
- **`pubspec.lock` commits with the `pubspec.yaml` change** that triggered it.
- **Never commit generated `*.g.dart` / `*.freezed.dart`.**
- **Never commit secrets.** Real tokens, DSNs, bearer headers, signing keys, cloud credentials. `env.example.json` is for variable names only.
- **Preserve unrelated dirty work.** Never restage or revert files you did not intentionally touch.

## Local Agent Scratch

Agents drop transient working files at repo root while in the middle of a task: `PLAN.md`, `TODO.md`, `NOTES.md`, `SCRATCH.md`. These reflect one session's in-flight reasoning. They are not durable design docs and should not enter git.

Add to `.gitignore`:

```
PLAN.md
TODO.md
NOTES.md
SCRATCH.md
```

- `AGENTS.md` is **durable** and stays committed. It is the canonical entrypoint, not scratch - do not add it to `.gitignore`.
- Durable architecture, decisions, and short-lived focus notes belong in `.context/` (committed). Scratch belongs at root (ignored).
- A plan worth keeping graduates into a dated design doc under `.context/active/` (see `.context/README.md`) or into the PR description before the scratch file is discarded. Do not park it in a root scratch file.

## Context Maintenance

- Keep `AGENTS.md` compact. Push detail into these files.
- Update `Commands` when `mise.toml` tasks or `pubspec.yaml` dependencies change.
- Update `.context/project-context.md` when architecture, integrations, or ownership shift.
- Record durable decisions (HTTP client, target platforms, flavors) in `.context/project-context.md`.
- In-flight specs, DDs, and TDDs live in `.context/active/`; see `.context/writing-specs.md#lifecycle` for naming and lifecycle.
